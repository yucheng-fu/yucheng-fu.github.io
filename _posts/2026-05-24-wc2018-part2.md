While the half volley itself requires lots of technique, I am also interested in examining the preceeding passes by answering the following questions:

1. Is it possible to quantify the difficulty or success probability of the passes that lead up the goal (i.e. how likely are these types of passes to succeed?)
2. If so, which of the passes would be considered more difficult?

Fortunately, there are lots of data related to passes in the ``statsbombpy`` API which we can leverage to adopt a data-driven approach to answer our questions. The plan is to build a machine learning model that estimates a pass difficulty score $p_\text{pass}$ for any pass from point $(x_1, y_1)$ to $(x_2, y_2)$ on the pitch. This score will help us quantify how challenging a pass is based on historical data and contextual features.

## Gathering the data
To estimate the success probability of a new pass, we first need to a dataset of historical passes. I wrote the following class to process a list of `match_ids` from the ``statsbombpy`` API and extract relevant information for each pass. Basically, the function in the class filters all match events for passes and stores the associated event features that may be useful for modelling pass completion probability. 

Below is a snippet of the class. The full implementation can be found [here](https://github.com/yucheng-fu/football_analytics/blob/main/src/utils/passes_handler.py).

```python
class PassesHandler:
    def __init__(self, match_ids: list[int]):
        self.match_ids = match_ids

    def get_passes_from_match_ids(self) -> pl.DataFrame:
        """Gatcher passes from all matches in the FIFA World Cup 2018

        Returns:
            pl.DataFrame: DataFrame containing all pass events
        """
        all_features = []

        for match_id in tqdm(self.match_ids):
            passes = self.fetch_passes_from_match(match_id=match_id)

            start_x, start_y = self.parse_pass_location(passes, col_name="location")
            end_x, end_y = self.parse_pass_location(passes, col_name="pass_end_location")
            length = self.parse_pass_length(passes)
            height = self.parse_pass_height(passes)
            angle = self.parse_pass_angle(passes)
            duration = self.parse_pass_duration(passes)
            body_part = self.parse_pass_body_part(passes)
            under_pressure = self.parse_under_pressure(passes)
            outcome = self.parse_pass_outcome(passes)
            match_ids_array = np.full(len(start_x), match_id)

            features = np.vstack(
                [
                    match_ids_array, start_x, start_y, end_x, end_y, length, height, angle, duration, body_part, under_pressure, outcome
                ]
            ).T

            all_features.extend(features)

        df = pl.DataFrame(
            all_features,
            schema=[
                "match_id", "start_x", "start_y", "end_x", "end_y", "length", "height", "angle", "duration", "body_part", "under_pressure", "outcome"]
        )

        # save to parquet
        df.write_parquet("../data/02-analysis/passes.parquet")

        return df
```
Below is a short summary of the selected features:
- ``start_x``: x coordinate of the pass origin (where the pass started)
- ``start_y``: y coordinate of the pass origin
- ``end_x``: x coordinate of the pass destination (where the pass ended)
- ``end_y``: y coordinate of the pass destination
- ``length``: length of the pass in yards
- ``height``: the height type of the pass (e.g., Ground Pass, Low Pass, High Pass)
- ``angle``: angle of the pass in radians, with 0 pointing straight ahead. Values between 0 and $\pi$ indicating an angle clockwise, and negative values between 0 and $-\pi$ representing an angle anti-clockwise.
- ``duration``: the length the event lasted in seconds
- ``body_part``: which body part was used to make the pass (Head, Left foot, Right foot, Other)
- ``under_pressure``: Boolean indicating whether the player making the pass was under pressure by other players. Null if False.
- ``outcome``: result of the pass (e.g., Incomplete, Out, Pass offside, null if completed). This is our target variable.

I did a full exploratory data analysis (EDA) to understand the data better by plotting feature distributions and checking for missing values. This will be useful for our modelling choices later. ## Data and modelling choices
Unfortunately, since this is a machine learning project, there are many boring choices and assumptions that need to be made before writing a single line of code. I think it is important to write down an initial design to set a clear direction of the project, especially in a machine learning project where a poorly designed ML pipeline can produce misleading or overly confident results due to model misconfigurations or data leakage. In the following paragraph, I share some of my considerations.

### Data
Passes are collected for all matches in the 2018 FIFA World Cup. The passes from the France - Argentina game are used as a separate hold-out test set, while passes from all remaining games were used to train the model. This setup also means that passes from France's subsequent matches in the tournament are included in the training data, despite occuring chronologically afte the France - Argentina match. I was initially hesitant to include these later matches, as doing so introduces information from future games into the training set. However, I work under the assumption that the underlying data-generating process for pass outcomes remains stationary throughout the tournament, such that the relation between input features and pass outcomes does not change during the tournament. 

Another limitation is that none of the features capture the position of opposing players on the pitch. Intuitively, defensive positioning is likely to have a big influence on the outcome of a pass. The `statsbombpy` API actually provides this information in the form of player positions for each event, called Statsbomb 360 data, but this is unfortunately only available for selected matches from 2020 and onwards. As a result, it is not possible to incorporate opponent positioning as a feature in the machine learning model.

The **target variable** is a binary label indicating whether a pass is completed successfully. Each pass event is assigned a value of 1 if the pass reaches its intended teammate and 0 otherwise. This formulation turns the problem into a binary classification task, where the model estimates the probability of successful pass completion given event-level features.

### Class imbalance
As the EDA reveals, the dataset has a substantial class imbalance. Approximately 80% of passes are successful, while only 20% are unssuccessful. To ensure that each training and validation split reflects the overall data distribution, I use `StratifiedKFold` from `sklearn.model_selection` to preserve the class proportion in all folds. 

### Model
Based on the exploratory data analysis, I will opt for using a gradient-boosted tree classifier as my base model. These types of models have a number of advantages over linear classifiers. Popular implementations of GBT models include LightGBM, XGBoost and CatBoost. The GBT classifers handle null values, are insensitive to feature scaling (due to splitting on value thresholds) and perform implicit feature selection (by preferentially splitting on informative features). It also supports native handling of categorical variables (when specified), providing an alternative for one-hot encoding.

I could explore other classification models, such as logistic regression, random forest etc, but in my experience the GBT classifiers usually perform very well on tabular data.

### Loss function
Given that I want to model the likelihood of completing a pass and not just a binary outcome (completed/failed), I have chosen to use NLL as the loss function. The NLL corresponds to maximising the likelihood given the model, encouraging well-calibrated probability estimates by heavily punishing overconfident incorrect predictions.

For a binary classification problem, the NLL loss function is defined as
\begin{equation}
\mathcal{L} = -\frac{1}{N} \sum_{i=1}^N [y_i \log{(\hat{y}_i)} + (1-y_i) \log{(1-\hat{y}_i})]
\end{equation}

Where $N$ is the number of samples, $y_i$ is the ground truth label for the $i$'th sample, and $\hat{y}_i$ is the model prediction for the $i$'th sample. The loss heavily punishes incorrect predictions made high confidence, encouraging the model to assign high probability to the correct class while remaining more well-calibrated. 

## Feature engineering
Feature engineering is the process of transforming raw data into more informative features that improve the performance of a machine learning model. Engineering good features can help models capture the underlying patterns in the data more effectively, leading to better generalisation and performance. It is important to distinguish between row-wise features and columnw-wise features, as naively creating features for a whole dataset can lead to data leakage, resulting in overly optimistic generalisation estimates.

### Row-wise features
Row-wise features are created using information from a single observation (row) only. These features include mathematical transforms, e.g. $\log{(x)}$ instead of $x$ and relationships, i.e. using distance and time to calculate a new velocity feature. Since these features are computed at the level of individual observations, they can be safely calcuated globally on the entire dataset.

### Column-wise features
Column-wise features on the other hand are created using information from an entire column or from the distribution of values across multiple observations. These features often capture global statistical properties of the data. Examples include standardisation of numerical variables (such as subtracting the mean and dividing with the standard deviation), and aggregated statistics (mean of value $x$ given varaible $y$, or frequency of a categorical variable). These features are susceptible to data leakage, if they are computed using the information from the full dataset. This is especially cross-validation loops where statistics must be recomputed separately within each training fold. 

### Engineered features
Based on my expertise in football and knowledge of mathematics and statistics, I engineered the following features:
- `log_velocity`: Log-transform of velocity computed using `length` and `duration`
- `angle_sin` and `angle_cos`:  Taking $\sin$ and $\cos$ of `angle`, so similar angles stay close in feature close. Currently, $\pi$ and $-\pi$ encode the same direction, but are very numerically different.
- `start_dist_to_goal` and `end_dist_to_goal`: Distance to the opposing goal for pass at the start and end to enocde attacking intention.
- `progressive_distance`: Progressed distance towards goal
- `direction_to_goal`: Based on angle, how alligned is the pass towards the opposing goal.
- `duration_x_under_pressure`, `log_velocity_x_under_pressure`, `length_x_under_pressure`: Interaction features, in this case two features multiplied together. 

### Automated feature engineering
I will also be using an automatic feature engineering method called [OpenFE](https://arxiv.org/abs/2211.12507). The method generates a large number of candidate feature using mathematical operations (multiply, divide, add, subtract), non-linear transformations (log, square root, sigmoid) and aggregation-based metrics (mean, max, frequency and group-by statistics). Candidate features are then evaluated using a baseline LightGBM model trained on the current features, and are ranked based on how well they reduce the model's error signal. The top $K$ most informative features are then selected and concatenatd with the original and used to train a second LGBM model, which are used to rerank all features, and top $K$ features are selected again.

The cool thing about OpenFE is that each feature is stored as a computational expression tree, where nodes represent operations and leaves represent the original features. This means that features can be deterministically reconstructed in a cross-validation setting, ensuring that the same transformation is applied consistently across folds without data leakage.

## Training and evalution specificaitons
### Training
In the following section, I describe the choices related to the training process. These decisions aim to ensure reproducible experiments, fair model comparisons and reliable estimations of generalisation performance.
- **Hyperparameter tuning**: I use `optuna` for hyperparameter tuning, because it is what I am familiar with. 
- **MLOps**: I will use MLFlow for experiment tracking and artifact management. Each training run logs parameters, metrics and model artifacts, while final models are logged to the model registry.
- **Training strategy**: Three types of experiments are performed:
    - Two-layer nested CV for estimating generaliation: A two-level nested K-fold cross-validation loop is used to get an estimate of the generalisation performance, while avoiding data leakage and preventing performance evaluation on the same data that is used for hyperparameter estimation.
    - Hyperparameter tuning: K-fold cross-validation is used within the training data to evaluate candidate hyperparameter configurations.
    - Training final model on full training set: Finally, we use the hyperparameters found in step 2 to train a final model on the full training set.

### Evaluation 
As mentioned previously, the France - Argentina passes are used as a hold-out evaluation set for the models. Due to the class imbalance in the dataset, overall accuracy is not a reliable evaluation metric. Instead, the focus is on evaluating how well the model distinguishes between classes and how well its predicted probabilities are calibrated. I consider the following:

- **Discrimination performance**: Measured using ROC-AUC, which evaluates the model's ability to distinguish between successful and unsuccessful passes across across classification thresholds. 
- **Calibration quality**: Assessed using reliability diagrams, which compare predicted probabilities against observed probability frequencies. In addition, expected calibration error (ECE) is used as a scalar summary of the calibration.
- **Classification metrics**: Measured using scalar metrics such as NLL, F1, recall, precision and accuracy.

- All gradient boosted tree models handle categorical variables well without one-hot encoding. This is in stark contrast to for example linear models that need one-hot encoding to handle nominal, categorical variables.

- LGBM offers the perfect combination of low training time and good performance wiht both default and tuned parameters.

There are three passes in this sequence: Kante → Matuidi → Lucas Hernandez → Pavard. 

In a simplified world, we discard the impact of the carries to the overall sequence. With an expected goal (xG) of $0.02415$ for Pavard's shot, that means the probability of scoring from this sequence is:
$$
P(\text{goal from full sequence}) = P(\text{goal | shot occurs}) \cdot P(\text{shot occurs}) = 0.02415 \cdot (0.99486 \cdot 0.63911 \cdot 0.73696) = 0.0113
$$
Or 1.13% chance.

## Conclusion
In the beginning of this projects, we wanted to answer two questions: 

1. Is there a way to quantify the difficulty of the two passes that lead up the goal (i.e. how likely are these types of passes to succeed?)
2. If yes, which pass was more difficult to make (has a lower probability of success)?

With regard to the first question, I show that it is absolutely possible to quantify pass difficulty for the build-up to the goal. The model I trained functions basically as an xPass model, analogous to xG in shot evaluation.

For the second question, we refer back to the final plot. Although Lucas Hernández's cross is impressive, the model assigns it a higher probability of success than Blaise Matuidi’s through ball. Based on our model's estimates, Matuidi's pass is therefore considered the more difficult of the two.
